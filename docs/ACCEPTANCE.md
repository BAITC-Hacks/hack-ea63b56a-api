# Приёмка умного подбора подрядчиков

Матрица предназначена для ручной приёмки и интеграционной проверки HackAlem AI #79-lite. Требования исходного DOCX отмечены `ТЗ`; уточнения API и реализации — `контракт`. Входы ниже проверены на `hackathon dataset anonymized.csv` (66 строк, 13 колонок). Совпадение CSV означает проверку локального исходного датасета и его Docker-копии без изменения оригинала.

## CSV-фикстуры и сценарии

Разделители `|` в `categories`, `event_formats`, `languages`, `busy_dates` означают списки. Попадание в составную категорию проверять по отдельному элементу списка, а не по сравнению со всей строкой. В таблице `population` — число профилей города/категории до прочих фильтров; `eligible` — после занятости и условий запроса.

| Сценарий | Валидный JSON запроса | Проверяемые ожидания по исходному CSV и ответу |
|---|---|---|
| Demo 1: плотная категория / базовый контракт | `{"city":"Алматы","date":"2026-10-15","eventFormat":"корпоратив","category":"Ведущий","budgetKzt":900000,"language":"русский"}` | `matched`; population 10, свободны 8, eligible ровно 3; известные eligible IDs: `HK-44923`, `HK-35215`, `HK-29829`; максимум 3, все цены ≤ 900000 и все IDs/поля сверены с CSV. Не фиксировать порядок без snapshot; одинаковый повтор обязан совпасть целиком. |
| Ranking stress (дополнительный, не замена demo из API-CONTRACT) | Тот же JSON, `budgetKzt: 1500000` | Population 10; по CSV есть 7 eligible кандидатов, из которых выбираются максимум 3. Проверить реальное ранжирование и grounded explanation; выбранные IDs должны входить в вычисленный eligible-набор. Этот вариант удовлетворяет требованию демонстрировать плотную категорию с конкурирующими кандидатами. |

Ответ и ID-список отличаются от Demo 1. |

UI показывает synthetic badge. Пустой `max_hours` не исключает по длительности. |
| Demo 3: кандидаты есть, все отфильтрованы | Demo 1, заменить `budgetKzt` на `1` | Валидный положительный integer, `no_candidates_after_filters`, population 10, eligible 0, пустой items и сообщение, что бюджет отсеял кандидатов; `exclusions.budget=10` по независимому подсчёту. Не HTTP 400. |

Подсчёты в сценариях относятся к исходному CSV: Алматы/Ведущий всего 10 из 15 ведущих по всем городам; Флорист/Астана — 1; инструменталиста в Астане нет. Основной dense-вход из `docs/API-CONTRACT.md` оставлен неизменным. Контрольный ranking stress вариант добавлен потому, что базовый вариант оставляет ровно 3 eligible профиля и сам по себе не проверяет отбор top-3 из большего числа кандидатов.

## Конкретные проверки

### API

- `GET /api/v1/health`: HTTP 200, `status="ok"`, `contractors=66`.
- `GET /api/v1/catalog`: города/категории/форматы/языки доступны; календарь ровно `2026-09-23..2026-12-31`.
- Три domain outcomes из сценариев выше: HTTP 200, верный status, coherent `count`, `eligibleCount`, `totalCandidates`, `message`, `exclusions`.
- Демонстрационный API запрос и cold request каждый укладываются в `<10s`; измерение выполнять клиентским таймером.
- Детерминизм проверять deep equality ответа, затем после restart. Проверять ещё concurrent duplicate requests при необходимости.
- Для любого результата вычислить допустимое множество из исходного CSV и запроса. Каждый `items[].id` должен входить в это множество и встречаться один раз. Сверить `anon_name`, city, category token, starting price и три quality flags по этому ID. Запретить неизвестный ID, смену цены, ложную доступность, ложный язык/формат/лимит часов или утверждение, что price-from — финальная цена.
- Объяснения: 1–2 русских предложения, попарно уникальны после удаления имён, содержат проверяемое профильное evidence из собственного description. Нельзя утверждать availability, опыт, специализацию, формат, язык, бюджетное соответствие или длительность без основания в запросе/соответствующих структурированных CSV полях. Отсутствующий `max_hours` пропускает duration-фильтр, но не доказывает неограниченную длительность.
- Пограничные запросы: impossible date и дата вне календаря → 400; budget не integer/≤0 → 400; заданная duration ≤0 или >24 → 400; отсутствующая/пустая категория и неизвестный город не должны превращаться в выдуманную категорию/профиль.

### AI и отказоустойчивость

- С выключенным AI (нет `OPENAI_API_KEY`) выполнить Demo 1: получить обычный валидный результат с `analysisMode="fallback"` и без сетевого запроса к OpenAI.
- С включённым AI выполнить ranking stress: `analysisMode="ai"`; структура валидна, все ID из eligible-set, карточки соответствуют CSV, порядок зафиксирован snapshot.
- В тестовой конфигурации с провайдером, который отвечает ошибкой или медленнее установленного deadline: endpoint укладывается в `<10s`, переключается на `fallback`, не возвращает сырой stack/error клиенту.
- Вызов AI не выполняется при `eligibleCount=0`; ожидаемый `analysisMode="not_needed"`.
- Повтор после первоначального fallback должен вернуть сохранённый fallback для того же ключа запроса; это ожидаемая воспроизводимость, даже если провайдер снова доступен.

### Frontend

- Главная страница загружается без browser console/page errors и горизонтального overflow при 1440, 390 и 320 px.
- Все обязательные поля можно заполнить; optional language/duration меняют ограничения только если заданы; invalid значения показывают ошибку формы/API.
- Dense показывает до трёх карточек с объяснениями; rare показывает одну карточку и synthetic badge; отсутствующая категория и all-filtered имеют различные заголовок/текст, не пустое состояние.
- Повтор одинакового поиска сохраняет порядок; смена даты на 20 декабря показывает отсутствие результата и занятость.
- Проверить через браузер Network/production bundle, что API key не раскрыт. Запросы браузера идут на same-origin `/api/v1/*`, а не прямо в Nest/OpenAI.
- Отобразить цену как «от» и quality flags/маркировку synthetic; не выдавать imputed price/city за подтверждённое значение без визуального флага.

### Docker / воспроизводимость

- `docker compose config --quiet` проходит.
- `docker compose up -d --build --wait` собирает и поднимает backend + frontend с health checks.
- Backend контейнер загружает 66 профилей из `/data/contractors.csv`; CSV скопирован из корня и не изменён. Frontend health проходит и server-side proxy достигает backend.
- `docker compose restart backend` не теряет снимки в named volume; тот же запрос после рестарта возвращает тот же JSON.
- `node scripts/smoke.mjs` проходит от начала до конца; проверяет health, catalog, dense, deep repeat, rare, budget-empty, no-category, date-shift, invalid date, frontend и proxy.
- `node scripts/browser-smoke.mjs` проходит на 1440/390/320 px: dense, repeat, December, rare, absent category, filtered, client errors и overflow.
- По завершении не считать только успешную сборку Docker достаточной: нужны живые API и браузерные smoke проверки.

Из корня репозитория, после сборки обоих приложений:

```sh
npm --prefix backend ci
npm --prefix backend run lint
npm --prefix backend test
npm --prefix backend run build
npm --prefix frontend ci
npm --prefix frontend run lint
npm --prefix frontend test
npm --prefix frontend run build

docker compose up -d --build --wait
node scripts/smoke.mjs
npm --prefix frontend exec -- playwright install chromium

```

Проверку AI fallback выполнять при пустом `OPENAI_API_KEY`, например запустить backend в отдельном терминале с переменной пустой и отдельным временным `CACHE_DIR`, затем послать Demo 1 и проверить `analysisMode`. Для живой AI-проверки задать ключ только в `backend/.env`, перезапустить backend и проверить `analysisMode="ai"`. Не печатать значение ключа и не добавлять его в frontend env.

Smoke имеет ожидание для dense `budgetKzt=900000`: ровно 3 результата, `totalCandidates=10`, `exclusions.busy=2`; rare ID `HK-90002` и одна synthetic карточка; December `exclusions.busy=8`; empty budget/status, отсутствующая категория, deep repeat, календарная валидация и frontend proxy. Browser smoke — пользовательские отображения тех же исходов. Команды unit/integration из пакетов обязательны при сдаче согласно `AGENTS.md`; приведённые здесь live checks дополняют их.

## Риски трактовки

- DOCX говорит «до трёх», а не «ровно три»; ровно три ожидается только в базовом dense-примере. Rare намеренно должен вернуть одну карточку.
- В ТЗ плотная категория «Ведущий — 15 профилей» указана по всему датасету; в Алматы CSV содержит 10, а всего ведущих 15. `totalCandidates` для конкретного города/категории поэтому 10.
- В DOCX редкие категории перечислены «по 3», но городское распределение может дать меньше; например Астане соответствует один флорист и ноль инструменталистов. Нельзя считать глобальную частоту результатом поиска по городу.
- Занятая дата не всегда сама по себе приводит к пустому ответу: проверять её по каждому ID; для выбранного декабрьского dense-входа все оставшиеся два свободных профиля исключаются бюджетом/форматом.
- Детерминизм LLM не следует из temperature=0; требование обеспечивается сохранённым snapshot. Ожидание одинаковых ответов действует при неизменных нормализованном запросе, dataset hash, модели, версиях prompt/pipeline и AI mode.
- Поле запроса со свободным текстом в MVP не предусмотрено контрактом. Поэтому «смысл описания» здесь — соответствие свободного description профиля типу мероприятия и структурированным условиям, не embedding search произвольного текста заказчика.
- В исходном DOCX баллы за AI входят в общую оценочную рубрику, однако обязательного использования конкретного провайдера, модели, embeddings или agentic orchestration нет. Проверять нужно фактически заявленный и работающий AI-анализатор; не подменять им обязательные hard filters.
- CSV `price_from_kzt`, `city_imputed` и `price_imputed` явно несут неопределённость. Интерфейс и объяснение должны сохранять смысл «цена от» и показывать соответствующие flags.
